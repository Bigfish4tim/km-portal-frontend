### 단계 4 — 세 층이 실제로 도는 것을 보이는 최소 기능

업무 화면이 아니다. 다만 **비밀번호 사전 검사는 B-2 가 그대로 쓰는 실물**이다.

**① `src/validation/password.ts`** — 근거: 백엔드 `util/PasswordPolicy.java`(선행조사 2-6). 🔴 구현 전에 그 파일을 직접 읽어 규칙 · 순서 · 문구를 대조한다. 다르면 코드를 따르고 보고한다.

- 입력: 비밀번호 · (선택) 아이디. 출력: 위반한 **첫 규칙 하나**의 식별자와 안내 문구 또는 "통과".
- 규칙과 순서(서버와 같다): 비어 있음 → 10자 미만 → 64자 초과 → 0x21~0x7E 밖의 글자(공백 · 한글 · 탭 포함) → 대 · 소 · 숫자 · 특수 중 3종 미만 → 아이디와 같음(대소문자 무시).
- 특수문자 = 0x21~0x7E 가운데 영문 · 숫자가 아닌 **전부**. 목록을 따로 적지 않는다.
- 안내 문구는 서버의 위반 문구와 **글자까지 같게** 한다(같은 규칙이 화면과 서버에서 다른 말로 나오지 않게). 문구 상수 위에 근거 줄 번호를 주석으로 단다.
- 입력을 `trim` 하지 않는다(`P12`).
- "지금 비밀번호와 다름" 규칙은 여기 넣지 않는다(서버만 안다 · 화면은 B-2 에서 두 칸의 비교만 한다).

단위 테스트(`src/validation/password.spec.ts`) — 🔴 비밀번호 값은 한눈에 가짜인 합성 값만 쓴다

| id | 무엇을 지키는가 |
|---|---|
| `PV-1` | 규칙 여섯 각각의 위반이 그 규칙으로 판정된다(표로 여러 값) |
| `PV-2` | 경계: 9자 실패 · 10자 통과 · 64자 통과 · 65자 실패 |
| `PV-3` | 여러 규칙을 함께 어기면 **앞의 것**이 나온다(예: 짧고 한글 포함 → 길이) |
| `PV-4` | 공백 · 탭 · 한글 · 전각 문자가 "쓸 수 없는 글자" 로 판정된다. 0x21 과 0x7E 는 통과한다 |
| `PV-5` | 3종 판정: 대 · 소 · 숫자(특수 없음) 통과 · 2종만이면 실패 · 영숫자가 아닌 임의의 ASCII 기호가 특수문자로 세어진다 |
| `PV-6` | 아이디와 대소문자만 다른 비밀번호는 실패 · 아이디를 주지 않으면 이 규칙을 건너뛴다 |
| `PV-7` | 앞뒤 공백을 잘라 내지 않는다(공백이 든 값은 통과하지 못한다) |

**② 서버 확인** — `src/api/serverCheck.ts`

- `GET /api/auth/me` 를 토큰 없이 부르고 **HTTP 상태 코드만** 돌려준다. 응답 본문은 읽지 않는다.
- 근거: 그 경로는 토큰이 없으면 401 봉투를 준다(선행조사 2-3 · `AuthController` — 구현 전에 직접 확인).
- 뜻: 401 = 백엔드가 살아 있고 프록시가 통한다 · 응답 없음 = 백엔드가 꺼져 있거나 프록시가 막혔다.

**③ 환경 점검 화면** — `src/views/EnvCheckView.vue`(임시 · B-2 에서 로그인 화면으로 바뀐다)

- Element Plus 부품으로 만든다: 제목 "환경 점검" · 비밀번호 칸(가림 입력) 하나와 그 아래 사전 검사 결과 한 줄 · "서버 확인" 단추와 결과 한 줄("서버 응답: 401(정상 — 로그인하지 않은 상태)" / "서버에 닿지 않습니다").
- 🔴 비밀번호 칸의 값은 화면 안의 변수에만 있다. 어디에도 보내지 않고 저장하지 않는다.
- 문구는 한 곳에 모은다.

**④ 화면 흐름 테스트** — `e2e/env-check.spec.ts` · 모의 응답은 `e2e/mocks/` 에, 각 파일에 근거 백엔드 파일:줄

|---|---|
| `EC-1` | `/` 를 열면 "환경 점검" 제목이 보인다 |
| `EC-2` | 짧은 값을 치면 길이 안내가 보이고, 규칙을 만족하는 값을 치면 통과 표시가 보인다 |
