### 2-2. 🔴 로그인 실패 — 다섯 가지가 `message` 로만 갈린다

전부 **401** 이고 전부 `ApiResponse.failure(메시지)` — 한 인자 `failure` 는 `errorCode` 를 `GENERAL_ERROR` 로 채운다(`J/dto/common/ApiResponse.java:195-197`).

| 경우 | 상태 | `errorCode` | `message` | 근거 |
|---|---|---|---|---|

| 비활성 | 401 | `GENERAL_ERROR` | 비활성화된 계정입니다. 관리자에게 문의하세요. | `:232-237` · `:265` |

| 🔴 비밀번호 만료 | 401 | `GENERAL_ERROR` | 비밀번호가 만료되었습니다. 재설정이 필요합니다. | `:245-250` · `:267` |

- **만료를 다른 401 과 구별할 단서**: `message` 문자열뿐이다. 상태 코드 · `errorCode` · `data` 는 다섯 경우가 같다. 이 문구는 백엔드 테스트 세 곳이 글자 그대로 고정하고 있다(`B/src/test/java/com/kmportal/backend/controller/LoginFailureLockTest.java:74` · `PasswordApiTest.java:76` · `PasswordRuleSitesTest.java:51`). 컨트롤러 주석도 "프론트는 이 응답을 받으면 만료 비밀번호 변경 창으로 보낸다" 고만 적는다(`:247`).
- **없는 아이디와 틀린 비밀번호**는 일부러 구별하지 않는다 — 구별하면 아이디의 존재가 드러난다(`:220-221`).
- **검사 순서**는 잠금 → 비활성 → 비밀번호 대조 → 만료다(`:159-163`). 그래서 만료 메시지는 비밀번호가 맞은 사람에게만 간다. 잠금 · 비활성 메시지는 비밀번호 대조 **전**에 나간다(같은 주석). `:234` 의 주석("비활성/잠금은 이미 자격증명을 아는 사람에게만 도달")은 이 순서와 맞지 않는다 — 백엔드 쪽 관찰이며 고치지 않는다.
- **5회 잠금**: 틀린 비밀번호만 센다. 기준은 5(`J/service/AccountSecurityService.java:50`). 5회째 실패의 응답도 "아이디 또는 비밀번호가…" 이고 그다음 시도부터 "잠긴 계정" 이다(`AuthController.java:225`). 자동 해제는 없다(`AccountSecurityService.java:26`). 로그인 성공은 실패 횟수를 0 으로 되돌린다(`:190-194`).
- **만료 변경 API 의 실패**(`:479-511`): 401 은 로그인과 같은 문구 · 같은 순서이고, 틀린 현재 비밀번호는 로그인 실패와 같이 센다(`:487-492`). 만료가 아닌 계정이면 400 "비밀번호 변경 대상이 아닙니다."(`AccountSecurityService.java:52` · `:132-134`), 규칙 위반도 400 이다(2-6).
- **본인 변경 API 의 실패**: 현재 비밀번호가 틀리면 400 "현재 비밀번호가 올바르지 않습니다." 이고 실패 횟수에 넣지 않는다(`AccountSecurityService.java:53` · `:148-163`). 401 이 아니다.

### 2-3. 요청마다 상태 확인 — 보호 API 의 401

필터가 요청마다 DB 에서 사용자를 읽는다(`JwtAuthenticationFilter.java:108`). 아래 어느 경우든 필터는 인증을 세우지 않고 지나가며, 응답은 엔트리 포인트가 만든다.

| 경우 | 응답 | 근거 |
|---|---|---|
| 토큰 없음 | 401 · `errorCode` `UNAUTHORIZED` · "인증이 필요합니다." | `J/exception/JwtAuthenticationEntryPoint.java:103-109` · `ApiResponse.java:234-236` |
| 토큰 만료 · 서명 오류 · 액세스 토큰이 아님 | 위와 같다 | 필터 `:104` · `:158-165` |
| 토큰의 사용자가 DB 에 없다 | 위와 같다 | 필터 `:110-113` |
| 비활성 · 잠김 · 비밀번호 만료 | 위와 같다 — "상태별 응답을 따로 주지 않는다" | 필터 `:115-120` · `J/entity/User.java:450-454` |

- 🔴 **토큰 만료 401 과 계정 상태 401 은 구별되지 않는다.** refresh 를 시도할지 가르는 단서가 응답에 없다.
- 그래도 흐름은 하나로 닫힌다: refresh 도 같은 상태 판정을 하고(`AuthController.java:326-330`), 상태가 나쁘면 401 "토큰 갱신에 실패했습니다."(`GENERAL_ERROR`)를 준다. 즉 "보호 API 401 → refresh 1회 → 성공이면 원 요청 재시도 · 실패면 토큰을 버리고 로그인 화면" 이면 된다. 사유(잠김 등)는 사용자가 다시 로그인할 때 2-2 의 메시지로 본다. 백엔드 명세도 같은 흐름을 적는다(`B/docs/명세/spec_20261117_a3_2d_auth.md:177`).
- refresh 의 실패 문구는 셋이고 전부 401 `GENERAL_ERROR` 다: "유효하지 않은 리프레시 토큰입니다."(`:308`) · "만료되었거나 유효하지 않은 리프레시 토큰입니다."(`:316`) · "토큰 갱신에 실패했습니다."(`:329` · `:357`).
- **예외 둘**:
  - `GET /api/auth/me` 는 `permitAll` 경로라 엔트리 포인트가 아니라 컨트롤러가 401 을 만든다. 문구는 같고 `errorCode` 가 `GENERAL_ERROR` 다(`:398-405` · `:418-423`). 🔴 프론트가 `errorCode === 'UNAUTHORIZED'` 로만 401 을 판별하면 이 경로를 놓친다. **상태 코드 401** 로 판별해야 한다.
  - 필터는 `/api/auth/login` · `/api/auth/refresh` 를 건너뛴다(필터 `:266-267`). 이 둘은 헤더의 토큰을 읽지 않는다.
- 권한은 토큰의 `roles` 가 아니라 DB 의 현재 역할로 만든다(필터 `:125-129`). 역할이 바뀌면 다음 요청부터 반영된다.

### 3-5. 토큰 보관 위치와 refresh 처리

사실(2-1): 토큰 둘이 본문으로 온다 · 쿠키 없음 · 액세스 토큰 안에 이름 · 이메일 · 부서가 있다 · refresh 토큰에는 아이디만 있다 · 로그아웃과 비밀번호 변경이 토큰을 무효로 만들지 않는다.

| 선택지 | 새로 고침(F5) | 걸리는 규칙 |
|---|---|---|
| (가) 둘 다 메모리 | 로그아웃된다 | 없음 |
| **(나) 액세스는 메모리 · refresh 는 `sessionStorage` (권고)** | 유지된다(refresh 로 액세스를 다시 받고 `GET /api/auth/me` 로 사용자 정보를 다시 읽는다). 탭을 닫으면 사라진다 | refresh 토큰에 아이디가 들어 있다 — `P6`(개인정보를 브라우저 저장소에 두지 않는다)에 아이디가 해당하는지 판단이 필요하다 |
| (다) 둘 다 `localStorage` | 유지된다 · 탭을 닫아도 남는다 | 🔴 액세스 토큰의 이름 · 이메일 · 부서가 저장소에 남는다 — `P6` 위반 |
| (라) refresh 를 httpOnly 쿠키로 | 유지된다 · 스크립트가 못 읽는다 | 백엔드 수정이 필요하다(`BR` 후보 · CSRF 대책 포함) |

- 권고 이유: (다)는 `P6` 에 걸리고 (가)는 업무 중 새로 고침마다 로그인해야 한다. (나)는 백엔드를 고치지 않고 둘 사이에 선다. `P6` 을 엄격히 읽는다면 (가)다.
- 사용자 정보(`user` 맵)는 어느 선택지에서도 저장소에 두지 않고 메모리에만 둔다.
- **refresh 처리 권고**(2-3 근거)
  1. 보호 API 가 **상태 401** 을 주면 refresh 를 한 번 부른다(`errorCode` 가 아니라 상태 코드로 판별).
  2. 동시에 여러 요청이 401 을 받아도 refresh 는 한 번만 나간다(진행 중인 약속을 함께 기다린다).
  3. 성공하면 원 요청을 한 번만 다시 보낸다. 다시 401 이면 포기한다.
  4. refresh 가 실패하면 토큰을 지우고 로그인 화면으로 간다.
  5. 로그인 · 만료 변경 · refresh 자신의 401 에는 refresh 를 시도하지 않는다(그 401 은 "토큰이 낡았다" 가 아니다).
  6. 이 로직과 토큰 읽기 · 쓰기는 한 모듈에만 둔다(`P5`).
- 화면의 권한 처리는 토큰의 `roles` 가 아니라 `GET /api/auth/me` 응답의 `roles` 를 쓰고, 그것도 편의로만 쓴다(`P8`).
