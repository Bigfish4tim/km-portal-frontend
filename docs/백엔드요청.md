# 백엔드 요청 — 프론트엔드에서 백엔드로

> 백엔드를 고쳐야 화면이 되는 상황을 적는 곳이다(`CLAUDE.md` 6-4).
> 프론트 세션은 백엔드를 고치지 않는다. 멈추고 여기에 적은 뒤 보고한다.

## 규칙

- 번호는 `BR-n` 이다(1부터 차례로 · 닫힌 번호를 다시 쓰지 않는다).
- 근거는 백엔드의 **파일:줄**로 적는다. 이름에서 짐작한 내용을 적지 않는다.

- `BR-7`(보호 API 401 의 원인 구별)은 **올리지 않는다**(2026-11-19 결정 10). 백엔드가 일부러 구별하지 않고, 흐름은 "401 → 재발급 1회 → 실패면 로그인 화면" 으로 닫힌다(선행조사 2-3). 번호는 다시 쓰지 않는다.

### BR-1 메모 — 2026-11-19 프론트 세션이 백엔드 작업 폴더에서 본 것 (읽기만 함)

- 백엔드 작업 폴더에 `BR-1` 을 반영한 것으로 보이는 코드가 **이미 있다.**
  - `dto/common/LoginFailureReason.java:31-46` — 사유 다섯과 `errorCode` 의 대응: `INVALID_CREDENTIALS` · `ACCOUNT_DISABLED` · `ACCOUNT_LOCKED` · `PASSWORD_EXPIRED` · `AUTHENTICATION_FAILED`. 문구와 상태(401)는 그대로다.
  - `controller/AuthController.java:221-255`(로그인의 실패 분기) · `:274-276`(`loginFailure`).
  - 테스트 파일 `src/test/java/com/kmportal/backend/controller/LoginErrorCodeTest.java` · `AuthControllerFailureCodeUnitTest.java` 가 있다.
- 🔴 **확인하지 못한 것**: 그 코드가 커밋 · push 됐는지, 백엔드 테스트가 통과하는지(이 세션은 백엔드에서 git · 테스트 명령을 실행하지 않는다). 그래서 상태를 "반영됨" 으로 바꾸지 않았다. 준호님이 백엔드 세션에서 확인한 뒤 바꾼다.
- `GET /api/auth/me` 의 401 · 재발급 실패 · 엔트리 포인트의 401 은 `BR-1` 의 범위 밖이다(`LoginFailureReason.java:25-27`). 화면은 그것들을 상태 코드로 판별한다.
- 2026-11-20(B-2a): `BR-1` 을 반영됨으로 바꿨다(명세 B-2a 6장의 지시). 위 메모는 기록으로 남긴다.
